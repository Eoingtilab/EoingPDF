# 2.4.2 일상 작업 신뢰성 검증

2026-10-14. 사용자가 평소 다루는 50페이지 이하 PDF를 중심으로 작업 조합과 입력 필드 보존을 검사했습니다. 모든 PDF의 완전한 호환성이나 경쟁 제품보다 우수하다는 판정은 아닙니다.

## 재현한 문제와 수정

| 문제 | 수정과 확인 |
|---|---|
| 역순 문서에서 입력 칸은 보이지만 실제 `/AcroForm` 필드 목록이 비어 있음 | 필드 트리를 유지하는 페이지 순서 변경 사용. 별도 PDF 라이브러리의 실제 필드 목록·값과 각 칸의 표시를 확인 |
| 한 필드가 여러 페이지에 표시된 문서를 추출·분할하면 서로 다른 이름의 필드로 바뀜 | 양식 문서 사본에서 페이지를 선택하여 원래 Parent/Kids 연결 유지. 일반 문서는 기존 페이지 복사 경로 사용 |
| 동일 필드의 반복 표시마다 입력창이 생겨 다른 입력이 덮어씀 | 실제 필드 객체 기준으로 입력창 통합. 충돌값 거부, 읽기 전용 공유 필드 보호 |
| 부모에서 상속된 선택 목록·다중 선택 저장값과 표시 불일치 | 상속 `/Opt` 읽기, 실제 필드의 `/V`·`/I`와 연결된 표시 갱신 |
| 긴 한글 입력이 64KiB 작업 통신 제한을 넘어서 실패 | 최대 4MiB로 조정. 유효한 큰 요청과 상한 초과 거부를 실제 자식 프로세스로 확인 |
| 앞쪽 페이지 삭제 후 현재 보고 있던 문서가 바뀜 | 원본 페이지 식별자로 현재 위치 유지. 현재 페이지 삭제 시 다음 남은 페이지, 끝에서는 이전 페이지 표시 |
| 판서 창의 닫기를 취소해도 부모 뷰어가 임시 PDF와 편집을 정리함 | 자식 창이 닫혔는지 먼저 확인. 취소 시 부모 닫기·저장 확인·자원 정리를 시작하지 않음 |
| 탐색한 모든 페이지의 썸네일과 닫힌 창 이미지가 계속 남음 | 최대 24개 카드 유지. 닫힌 창의 썸네일·페이지 래스터·타이머 해제 |

## 일상 작업과 양식 검증

- 생성한 8·50페이지 PDF에서 직인 → 워터마크 → 실제 작업 프로세스 한글 양식 입력 → 페이지 정리 → 실행 취소/재실행 → 사본 저장을 연결했습니다.
- 저장된 실제 필드값, 화면 표시, 텍스트, 링크, 회전, CropBox, 메타데이터와 원본 SHA를 확인했습니다. 취소·잘못된 암호·저장 실패는 기존 편집 상태를 유지해야 합니다.
- 부모/자식 공유 필드, 동일 페이지 반복 표시, 저장 최적화로 공유된 위젯 참조, 읽기 전용, 상속 선택 목록·다중 선택을 검사합니다. 이름만 같은 독립 필드를 임의로 합치지 않습니다.
- 암호 유무와 회전·자르기가 섞인 양식에 역순·워터마크·여백 자르기·메타데이터 제거·복구·페이지 번호·암호 설정을 적용합니다. 분할 결과의 페이지와 남은 필드 연결을 검사합니다.
- pypdf의 독립 읽기와 PyMuPDF 실제 렌더링을 함께 사용합니다. 외부 앱에서 모든 양식 유형을 직접 조작한 결과를 뜻하지 않습니다.
- 원본 바이트를 보존하고, 취소·실패한 출력은 게시하지 않습니다. 실제 개인 문서는 수집하지 않았습니다.

## 썸네일 자원 전후 비교

비교 대상은 v2.4.1의 뷰어와 2.4.2 수정 뷰어입니다. 동일한 생성 PDF·측정 스크립트를 각각 새 프로세스에서 실행했습니다. Windows, Python 3.12.14, PyMuPDF 1.27.2.3, 논리 CPU 16개 환경의 Qt offscreen 측정입니다. 프로세스 작업 집합은 Win32 `GetProcessMemoryInfo`로 읽었습니다. 앱 시작·라이선스·OCR·네트워크 시간은 포함하지 않습니다.

| 문서 | 썸네일 카드 | 썸네일 픽셀 바이트 | 프로세스 작업 집합(바이트) |
|---|---:|---:|---:|
| 일상 50페이지, 40,607B | 50 → 24 | 2,868,864 → 1,387,136 | 113,819,648 → 109,289,472 |
| 보조 일반 1,000페이지, 815,157B | 1,000 → 24 | 57,606,400 → 1,387,136 | 249,065,472 → 119,377,920 |
| 보조 스캔형 60페이지, 38,641,662B | 60 → 24 | 3,525,120 → 1,410,048 | 307,351,552 → 301,568,000 |

1,000페이지 썸네일 전체 탐색은 4.3851초 → 3.4997초였습니다. 50페이지 이동 중앙값은 4.7ms → 5.1ms, 스캔형은 27.7ms → 27.3ms로 일상 이동 속도 향상을 주장하지 않습니다. 모든 수정 사례에서 닫힌 창의 카드는 0개이고 페이지 래스터가 해제됐습니다. Windows 할당자와 문서 이미지 캐시 때문에 프로세스 메모리가 즉시 0이 되지는 않습니다.

재현 도구는 `tests/viewer_performance_smoke.py`입니다. 원시 기록은 `temp/reliability/perf-before-{daily,text,scan}.json`과 `perf-after-{daily,text,scan}.json`에 있습니다. 이 측정은 특정 생성 문서의 단회 비교이며 모든 문서의 자원 상한이나 속도 보장은 아닙니다.

## 배포 검증과 남은 범위

전체 자동 검사 688개가 통과했습니다(실패 0, 건너뜀 0, JUnit 119.770초). 관련 양식 검사 86개와 별도 일상 작업 12개·뷰어 자원 4개·큰 요청 2개를 포함합니다. 실제 Word가 내보낸 기존 시험 표도 입력 칸 3개 생성 → 한글 입력 → 역순 후 실제 필드값과 원본 보존을 확인했습니다.

Windows 화면 검사에는 실제 50페이지 탐색·썸네일 재표시·판서 종료 확인창의 취소 버튼 클릭·직인/판서/편집 기록 유지·닫힌 창 자원 해제를 추가했습니다. 기존 세 언어·두 테마의 작업 화면, 판서 GPU, 클립보드, 암호·양식·설정·라이선스 화면 검사도 통과했습니다. 라이선스는 개인 계정 상태를 바꾸지 않는 시험 저장소/게이트를 사용했습니다.

최종 배포 검증 결과와 설치형·포터블 해시는 공식 배포 저장소의 [2.4.2 검증 기록](https://github.com/Eoingtilab/nalapps-releases/blob/main/products/eoingpdf/2.4.2/validation.json)에 기록합니다. 배포 전에 전체 자동 검사, Windows 화면 검사, 두 실행파일의 양식·검색·OCR·업데이트 복구 검사를 실행합니다. 게시 후 실제 업데이트 경로에서 두 파일을 다운로드하고 크기·SHA-256을 확인합니다.

사용자별 실제 PDF, 모든 한글/Office 출력, 인증서 서명·XFA 양식, 외부 뷰어의 모든 동작, 기존 설치의 실제 교체·제거는 이번 범위에 포함하지 않았습니다. 대용량 양식 분할은 필드 트리 보존을 위해 압축 문서 사본을 사용하므로 문서 크기에 따른 임시 메모리 비용이 있습니다. 전문 객체 편집·외부에서 저장된 워터마크 자동 식별·삭제 등 기존 미구현 범위는 계속 별도 과제입니다.

일부 목록 상자는 실제 선택값과 입력창의 선택이 유지되지만, MuPDF의 정적 표시에서 선택행 배경 강조가 나타나지 않을 수 있습니다. 선택 항목은 양식 입력창에서도 확인할 수 있습니다.

공유 필드의 원래 관계 유지는 중복 없는 페이지 선택에 적용합니다. 같은 페이지를 반복 추출하면 기존 복사 방식으로 별도 필드를 생성하며, 반복 사본의 입력값을 자동으로 하나로 연결하지 않습니다.
