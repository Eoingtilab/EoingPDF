# Direct2D 판서 진행 및 검증

2026-09-14 소스 작업이며 기존 배포 설치 파일에는 아직 포함되지 않았습니다.

## 구현

`native/InkOverlay.cpp`는 별도 상주 프로세스 없이 현재 UI 스레드에서 동작하는 소유 팝업 창을 만듭니다. 평상시는 `WS_EX_TRANSPARENT`와 `HTTRANSPARENT`, 판서 모드는 입력 포착으로 전환하며 포커스를 빼앗지 않습니다. 현재 기본 경로는 `GpuInkSurface.h`의 Direct3D 11 + Direct2D + DirectComposition GPU 합성입니다. 하드웨어 초기화가 불가능하면 Direct2D DC render target과 알파 비트맵, `UpdateLayeredWindow` 경로로 돌아갑니다.

투명 창의 판서 입력은 `ink_controller.py`를 통해 기존 페이지별 판서 모델에 전달됩니다. 저장은 `presentation_ink.py`의 회전 좌표 변환과 암호 보존 경로를 사용합니다. 창이 숨겨지면 타이머와 네이티브 창을 정리합니다. Windows Qt 플랫폼에서 사용하며 offscreen 검증과 네이티브 로딩 실패 시 기존 Qt 렌더링을 사용합니다.

좌표는 Qt 위젯의 실제 HWND 클라이언트 크기와 `ClientToScreen`으로 계산합니다. 네이티브 창은 페이지 영역만 덮습니다. 배율이 다른 실제 모니터 사이 이동은 아직 검증하지 않았습니다.

한 프레임 최대 250,000점/10,000획, 16,777,216픽셀의 네이티브 입력 크기 제한과 유효 좌표 검사가 있습니다. 전체 발표 세션 메모리 제한은 아직 없으며 별도 구현이 필요합니다.

## 검증 증거

- `native/build_ink.cmd`: MSVC x64 DLL 컴파일 성공.
- `QT_QPA_PLATFORM=offscreen python -m pytest tests/test_native_ink.py tests/test_presenter_ink.py -q -p no:cacheprovider`: 16개 통과.
- 네이티브 알파 픽셀·크기 변경·잘못된 입력 거부, 클릭 통과 스타일 전환, HWND 입력 메시지→판서 좌표 연결, 핸들 폐기를 검사합니다. 실제 물리 마우스로 화면을 조작한 증거는 아닙니다.
- 빌드 스크립트는 네이티브 DLL을 먼저 컴파일한 뒤 검증·패키징합니다. 최종 패키징 검증은 아직 남아 있습니다.

## 성능 측정과 미달 사항

`python scripts/benchmark_native_ink.py`로 1,000점, 준비 5회 후 20회 측정했습니다. Python→DLL 데이터 전달과 숨겨진 레이어 창 제출을 포함하며 모니터 실제 표시 FPS나 입력 지연 측정이 아닙니다.

| 크기 | 중앙값 | 최대 | 120fps의 8.33ms 예산 |
| --- | --- | --- | --- |
| 1920×1080 | 5.776ms | 7.874ms | 이 측정에서는 이내 |
| 3840×2160 | 19.145ms | 22.002ms | 미달 |

현재 방식은 4K에서 120fps를 충족하지 못합니다. 전체 비트맵 전송을 줄이는 GPU 합성 방식과 획 캐싱, 실제 고주사율 모니터 측정이 필요합니다. 8ms 단발 타이머는 변경 요청을 합치는 용도이며 120fps 달성의 증거로 사용하지 않습니다. 스냅·형광펜·텍스트·고스트 잉크도 아직 남아 있습니다.

API 근거: [Microsoft Direct2D DC render target](https://learn.microsoft.com/en-us/windows/win32/api/d2d1/nn-d2d1-id2d1dcrendertarget).

## 변경 없는 프레임 생략과 부분 갱신 실험

동일한 점·획 경계·펜 너비·입력 모드·화면 크기의 프레임은 이제 다시 그리거나 제출하지 않습니다. 크기, 획 묶음, 모드가 바뀌면 캐시를 무효화합니다. 캐시 복사 중 할당 실패도 C++ 예외가 DLL 경계를 넘지 않도록 처리합니다.

부분 영역 렌더링은 실험 후 제거했습니다. 첫 구현은 겹치는 획에서 전체 렌더링과 일부 픽셀이 달랐고, 고정 영역으로 나눈 후에는 픽셀은 일치했지만 전체 갱신이 크게 느려졌습니다. 배포할 소스에는 이 실험 경로를 남기지 않았습니다.

측정 도구도 같은 그림 반복만 측정하던 방식에서 변경 없음/새 점 추가/기존 점 변경으로 나눴습니다. 변경 없는 프레임의 빠른 반환 시간을 실제 판서 FPS로 해석하면 안 됩니다. 현재 전체 렌더링 경로의 재측정 결과:

| 크기 | 작업 | 중앙값 | 최대 |
| --- | --- | --- | --- |
| FHD | 변경 없음 | 0.431ms | 0.882ms |
| FHD | 새 점 추가 | 4.561ms | 5.668ms |
| FHD | 기존 점 변경 | 4.926ms | 6.664ms |
| 4K | 변경 없음 | 0.419ms | 3.739ms |
| 4K | 새 점 추가 | 16.788ms | 19.283ms |
| 4K | 기존 점 변경 | 16.717ms | 20.386ms |

이 측정은 GPU 합성 도입 전 DC 경로입니다. 당시 4K/120fps는 미달이었습니다. 변경 시퀀스별로 새 렌더러와 모든 픽셀을 비교하는 검사는 유지합니다.

## GPU 합성 구현 및 재측정

Direct3D 11 하드웨어 장치에 BGRA 텍스처를 만들고 Direct2D로 그린 후, GPU 내부에서 합성용 flip swap chain으로 복사하여 DirectComposition에 제출합니다. 일반 프레임은 CPU로 픽셀을 읽지 않습니다. `pixels()`는 검사에서만 별도의 staging 텍스처로 읽습니다. 창 크기 변경 시 버퍼를 재생성하고, 종료 시 GPU/합성 자원과 HWND를 해제합니다. 런타임 오류가 발생하면 판서 데이터는 유지하고 Qt 렌더링으로 전환합니다.

GPU 사용을 강제한 검사와 DC 사용을 강제한 검사를 모두 수행했습니다. 대체 경로가 실행된 결과를 GPU 성공으로 취급하지 않습니다.

- `test_native_ink.py` + `test_presenter_ink.py`: 29개 통과. 각 백엔드의 편집 시퀀스, 픽셀·투명도, 캐시 무효화, HWND 입력 전달, 클릭 통과 hit test, 자원 해제를 검사합니다.
- `tests/native_ink_ui_smoke.py`: 실제 Windows Qt 창에서 GPU 선택, 렌더링된 선의 알파값, 네이티브 입력, 창 이동, B 전환, 판서 해제 시 hit test, 종료 후 HWND/타이머 해제 통과. 입력 메시지는 합성이므로 물리 입력 검증은 아닙니다.
- 배포 빌드에 Windows GPU UI 검사를 추가했습니다. GPU가 있는 Windows 데스크톱 빌드 환경이 필요합니다.

동일한 1,000점 시작 조건에서 새 점을 추가하거나 기존 점을 바꾸며, 5회 준비 후 20회 측정했습니다. GPU 명령 완료를 기다린 시간을 포함합니다.

| 크기 | 작업 | DC 중앙값/최대 | GPU 중앙값/최대 |
| --- | --- | --- | --- |
| FHD | 새 점 추가 | 4.667 / 5.970ms | 1.496 / 3.467ms |
| FHD | 기존 점 변경 | 4.702 / 11.744ms | 1.351 / 14.645ms |
| 4K | 새 점 추가 | 17.674 / 20.114ms | 1.687 / 4.313ms |
| 4K | 기존 점 변경 | 17.818 / 32.896ms | 1.608 / 6.203ms |

4K의 이 두 작업은 측정 중 8.33ms 예산 이내였지만 FHD 변경 작업에는 긴 프레임도 있었습니다. 적은 횟수의 숨겨진 창 측정으로 물리 모니터의 지속 120fps를 증명하지 않습니다. 듀얼 4K·장시간 입력·스케줄링 지연·장치 손실 실험과 전체 판서 도구 구현은 계속 남아 있습니다.

GPU API 근거: [Microsoft flip swap chain](https://learn.microsoft.com/en-us/windows/desktop/api/dxgi/ne-dxgi-dxgi_swap_effect).
