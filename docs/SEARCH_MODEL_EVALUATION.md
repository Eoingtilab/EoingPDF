# 로컬 의미 검색 모델 평가

## 2026-09-15 첫 후보

소스: [Sentence Transformers static-similarity-mrl-multilingual-v1](https://huggingface.co/sentence-transformers/static-similarity-mrl-multilingual-v1), 고정 revision `b68f4122911bcffcd6e1f695f2d99cd6788972d8`, Apache-2.0. 공식 모델 카드에 한국어 지원과 Matryoshka 차원 축소가 명시되어 있다. 다만 저자는 검색 전용 모델이 아니라고 명시하므로 실제 질의/문서 평가가 필요하다.

`scripts/prepare_search_model.py`는 공식 원본 SHA-256을 확인하고 256차원 토큰별 대칭 int8 ONNX로 변환한다. 전체 테이블을 float로 복원하지 않고 요청 토큰만 Gather 후 역양자화한다. 모델은 27,529,075 bytes이며 평가 산출물은 `temp/search-model`에만 둔다. 앱이나 설치파일에 포함하지 않았다.

`scripts/evaluate_search_model.py`에서 한국어 업무 문장 10개와 어휘가 다른 질의를 별도 프로세스로 평가했다. 이는 소규모 개발 평가이며 품질 보증용 대표 데이터셋이 아니다.

- 첫 결과 정답: 7/10. 나머지 세 질의는 두 번째 순위였다.
- 초기화: 약 108ms, 10개 문서 점수 계산 포함 질의 중앙값: 약 0.14ms.
- 단일 BLAS 스레드 실행 RSS: 103,911,424 bytes, 최대 RSS: 128,868,352 bytes, private bytes: 80,486,400.
- 기본 BLAS 스레드에서는 private bytes가 약 586MB였으므로 추론 프로세스 시작 전 단일 스레드 설정이 필요하다.

판정: I-02 완료 아님. 최대 메모리 100MB 제한을 충족하지 않고 검색 품질도 충분히 입증하지 못했다. 이 후보를 제품의 완성된 시맨틱 검색으로 배포하지 않는다. 다음은 검색에 맞춘 다국어 모델 후보 비교 및 더 큰 한국어 질의 평가, 이후 문서 인덱스·페이지 하이라이트·UI 연결이다. 기존 381개 테스트 통과 설치파일에는 이 평가 작업이 들어 있지 않다.

재현용 패키지는 `scripts/requirements-search-evaluation.txt`, 실행 결과는 `temp/search-model/evaluation.json`에 기록된다. 모델 다운로드 시 사용자 문서나 질의는 전송하지 않으며 추론 평가에는 네트워크가 필요 없다.

## PDF 색인 엔진 연결

`src/eoingpdf/semantic_search.py`에 로컬 ONNX 실행 및 SQLite 구간 색인을 구현했다. 폴더의 PDF 텍스트 블록을 최대 1,000자 구간으로 나누고 페이지 번호·블록 좌표·벡터를 저장한다. 후보 벡터는 순차 읽기와 제한된 힙으로 계산한다. 2,000개 문서·문서당 10,000페이지·총 100,000구간 제한을 적용하고, 입력 취소는 색인 트랜잭션 전체를 롤백한다.

모델/폴더가 바뀌면 다시 색인하고, 바뀌지 않은 파일은 SHA-256으로 재사용한다. 삭제되거나 새로 암호가 걸린 파일은 색인에서 제거한다. 반환 후보도 현재 파일 해시와 대조하므로 취소로 이전 색인이 남아 있어도 변경된 문서의 오래된 내용은 반환하지 않는다. 상위 후보를 제한하므로 오래된 문서가 많으면 요청한 개수보다 적은 결과를 반환할 수 있으며 이 경우 재색인이 필요하다.

`tests/test_semantic_search.py` 4개 통과: 가짜 임베딩이 아닌 실제 평가 ONNX 모델 → 한국어 PDF 두 개의 검색 → 올바른 페이지 및 텍스트 영역 검증, 원본 보존, 재색인 재사용, 새 암호/삭제 처리, 취소 롤백, 손상 벡터 거부. 모델 준비가 없는 환경은 명시적으로 skip한다. 암호 입력 및 OCR 색인, UI와 실제 뷰어 하이라이트, 모델 품질/100MB 메모리 목표, 배포 연결은 아직 미완료다. 모델과 색인 엔진을 정식 기능으로 노출하지 않았다.

## 뷰어 검색 영역 표시

PdfViewer.show_search_result는 경로와 현재 파일 SHA-256, 페이지 및 좌표를 검증한 뒤 일치 페이지를 열고 텍스트 블록을 반투명 노란색으로 표시한다. 강조는 화면 오버레이이며 PDF에는 기록하지 않는다. 회전 행렬로 표시 좌표를 변환하고, 긴 페이지의 일치 영역까지 자동 스크롤한다. 확대/축소 후에도 위치를 유지하고 다른 페이지에서는 표시하지 않는다.

tests/test_search_highlight.py의 0/90/180/270도·CropBox·확대·실제 강조 픽셀·화면 내 위치·원본 보존·변경된 파일 거부 검사와 기존 휠/실제 ONNX 검색 검사 합계 13개 통과. 검색 창 및 작업 프로세스 연결은 아직 남아 있다.

## 검색 프로세스 격리

--search-child는 하나의 색인/검색 요청만 stdin으로 받고 종료한다. Qt 검색 작업자는 기존 Job Object 격리와 취소 파일 프로토콜을 재사용한다. 검색 자식에서 NumPy 로드 전에 BLAS 스레드 수를 제한하며, 모델·질의·문서 내용은 외부로 보내지 않는다. 결과 메시지와 경고 목록 크기를 제한했다. 취소 후 강제 종료 타이머는 작업자 소유로 변경하고 완료 시 중지하여 삭제된 Qt 객체에 늦은 콜백이 발생하지 않도록 했다.

실제 SearchWorker → 새 ONNX 프로세스 → SQLite 색인 → 검색 결과 경로, 즉시 취소, 잘못된 요청, 자식 종료 및 임시 디렉터리 정리 검사를 포함해 검색/기존 변환 프로세스/강조 표시 검사 16개 통과. 검색 창 및 정식 모델 채택은 아직 남아 있다.

검색 화면(SearchDialog)을 추가하고 실제 폴더 선택 → 색인 자식 → Enter 검색 → 결과 페이지 열기·강조 → 취소·닫기까지 연결했다. 실제 ONNX 모델을 사용하는 UI 검사와 검색 관련 검사 합계 13개 통과. 작업 중 창 닫기는 취소와 자식 종료를 기다리고, 다시 열 때 닫기 상태를 초기화한다. 품질·메모리 목표 검증 전이므로 메인 메뉴 및 배포 모델에는 아직 연결하지 않았다.

## 외부 가중치 메모리 매핑 (2026-09-15)

prepare_search_model.py --external은 큰 가중치를 외부 weights.bin에 저장해 ONNX 런타임의 외부 데이터 로드를 사용한다. 모델 그래프는 644 bytes, 가중치는 별도 파일이며 둘 다 SHA-256 검증과 모델 식별값에 포함된다. 영어·한국어·일본어 출력 벡터는 인라인 모델과 비트 단위로 동일하며, 손상된 가중치는 거부한다. 실제 두 모델의 색인 테스트 포함 9개 통과.

모델 단독 평가 최대 RSS는 88,006,656 bytes로 감소했다. PDF 생성용 프로세스를 측정 대상 밖으로 분리하고 30개 PDF·300페이지 색인과 검색까지 실행한 최대 RSS는 111,407,104 bytes, private bytes는 88,391,680이었다. 색인 약 642ms, 검색 중앙값 약 21ms다. 30개 파일은 같은 10개 한국어 페이지의 복제이므로 문서 다양성·대규모 품질 증거가 아니다. 전체 작업 RSS 100MB 목표는 아직 미달이며, PDF 추출과 임베딩 단계의 메모리 중첩을 줄이는 구조 개선이 필요하다. 검색 정답 순위는 기존 7/10 첫 결과, 10/10 상위 두 결과와 동일하다.

## 단계별 색인 준비·게시

search_staging.prepare는 ONNX 런타임을 읽지 않고 PDF 텍스트를 임시 SQLite에 추출한다. complete는 PyMuPDF를 읽지 않고 남은 임베딩을 계산한 뒤 색인을 교체한다. 미완료 색인은 검색할 수 없고, 취소·모델 불일치·다른 작업의 색인 변경 시 원래 색인을 덮어쓰지 않는다. 게시 시 Windows 파일 잠금과 기준 해시를 함께 사용한다. OS가 잠금을 회수하므로 중단된 프로세스가 잠금을 영구 점유하지 않는다.

실제 두 개의 순차 Python 프로세스에서 각 단계가 반대쪽 엔진을 import하지 않는 것을 확인했다. 이전 모델 테스트 포함 11개 통과, 게시 잠금 추가 후 단계 검사 2개 재통과. UI 작업자가 아직 이 새 두 단계 경로로 전환되지 않았으며, 전환 후 전체 작업 메모리를 다시 측정해야 한다.

### 검색 화면의 순차 프로세스 연결

SearchWorker의 build 요청을 prepare(문서 추출)와 complete(임베딩)의 두 프로세스로 분리했다. 첫 프로세스가 종료되고 작업 범위가 해제된 뒤 두 번째 프로세스를 시작한다. 색인은 최종 저장 폴더와 같은 볼륨의 임시 폴더에 작성하고 완료 시 원자적으로 교체한다. 화면 진행률은 두 단계를 합산하며, 취소·실패는 한 번만 알리고 임시 폴더를 정리한다. 임시 폴더 생성 실패도 화면에 전달한다.

검증: search_process, search_staging, search_ui의 7개 테스트 통과. 실제 자식 프로세스 분리, 화면 검색/결과 열기, 취소, 저장 충돌, 임시 경로 실패, 완료 후 임시 폴더 제거를 확인했다. 이 연결 이후의 전체 메모리 재측정과 실무 검색 품질 검증은 아직 남아 있다. 모델은 평가용이며 정식 설치 파일에는 포함하지 않았다.

### 순차 파이프라인 실측

`scripts/benchmark_search_pipeline.py`로 실제 search_child 프로토콜을 실행하고 각 프로세스의 Windows peak working set을 수집했다. 10쪽 PDF 30개(복제본 300쪽), 외부 가중치 ONNX 기준 결과:

| 단계 | 최대 RSS(bytes) | 프로세스 시작 포함 소요(ms) |
| --- | ---: | ---: |
| 문서 추출 | 54,796,288 | 1,640 |
| 임베딩 및 색인 교체 | 85,016,576 | 3,051 |
| 질의와 결과 반환 | 84,926,464 | 888 |

각 단계에서 MuPDF와 ONNX가 동시에 로드되지 않았고, 질의 결과의 정답 페이지도 확인했다. 계측용 psutil은 포함하지만 데스크톱 UI 메모리는 포함하지 않는다. 따라서 검색 자식 프로세스는 이번 표본에서 100MB 이하이며 앱 전체 또는 모든 입력의 100MB 보장을 뜻하지 않는다. 복제 문서 표본은 검색 정확도나 일반적인 업무 성능의 증명이 아니다. 원시 측정값은 temp/search-model/external/evaluation-staged.json에 기록한다.

검색 화면에 선택 폴더의 검색 자료 삭제를 추가했다. 확인 후 해당 폴더의 해시 이름 SQLite 파일만 삭제하며 원본 PDF와 다른 캐시는 유지한다. 작업 중 버튼을 비활성화하고 저장과 동일한 잠금을 사용한다. 기존 색인을 읽은 다른 작업은 삭제 이후 저장 시 기준 해시 불일치로 거부된다. 경로 및 파일 이름 검증으로 캐시 밖 파일 삭제를 거부한다. 이 기능은 일반 파일 삭제이며 디스크의 물리적 보안 삭제를 보장하지 않는다.

동일 프로세스 연속 호출 검사에서 준비 단계의 SQLite 연결이 context manager 종료만으로 닫히지 않아 Windows 파일 교체를 막는 문제를 발견했다. 명시적으로 연결을 닫도록 수정했다.

### 이미지 PDF 검색

검색 화면의 ‘스캔 PDF 글자 인식 포함’ 옵션으로 Windows 로컬 OCR을 사용한다. 기본은 빠른 텍스트 추출이며, 옵션을 켜면 텍스트 블록이 없는 이미지 페이지에만 OCR을 호출한다. 페이지 회전 행렬을 역으로 적용해 OCR 결과를 원본 PDF 좌표로 색인하므로 결과 강조 표시와 연결된다. 원본 파일에는 OCR 레이어를 쓰지 않는다. 옵션 변경 시 색인 정책을 변경해 기존 텍스트 전용 색인을 재사용하지 않는다. 언어 팩 부재나 인식 실패는 해당 문서 제외 사유로 알린다.

검색 OCR 테스트에는 실제 Windows OCR 실행과 0/90/180/270도 좌표 변환 검사가 포함된다. 스캔 모드의 OCR 보조 프로세스 메모리·전체 처리 속도는 앞선 텍스트 PDF 측정에 포함되지 않으며 별도 측정이 필요하다. 텍스트와 스캔 이미지가 한 페이지에 혼합된 문서에서 이미지 속 추가 텍스트를 추출하는 기능은 아직 없다.

### 혼합 페이지 OCR 보완

위 이미지 PDF 절의 혼합 페이지 제한을 보완했다. OCR 옵션을 켜면 실제 표시되는 이미지가 있는 페이지를 인식하며, 네이티브 텍스트와 OCR 단어의 좌표 겹침을 비교해 중복 단어를 제외한다. 이미지가 없는 텍스트 페이지에는 OCR을 호출하지 않는다. 인식 정책을 ocr-v2로 변경해 이전 색인을 갱신한다. 실제 Windows OCR 혼합 페이지와 이미지 전용 PDF → 색인 → 검색을 검증했고, 관련 OCR/프로세스/UI 13개 테스트가 통과했다. 네이티브/OCR 텍스트 중복 제거는 위치 겹침 휴리스틱으로, 특수 조판·겹쳐진 문자에서는 추가 검증이 필요하다.

### 앱 및 패키징 연결

메인 사이드바의 문서 내용 검색에서 검색 화면을 열도록 연결했다. 라이선스 확인 후 사용하며 앱 시작 때 모델을 로드하지 않는다. assets/search에 고정 해시의 외부 ONNX 모델, 가중치, 토크나이저 및 출처/변경/라이선스 파일을 준비했고 기본 경로의 실제 검색 UI 테스트를 통과했다. 빌드 시작 시 package_search_model.py --verify가 모델 해시와 필수 고지를 검사한다. ONNX Runtime 및 tokenizers 런타임 의존성을 추가하고 소스 패키지에도 모델을 포함하도록 변경했다.

이는 기능을 앱에 연결한 상태이며, 모델 정확도 검토가 완료됐다는 의미는 아니다. 기존 provenance의 evaluation-only 표시는 유지한다. 새 frozen 실행파일의 검색 검증 및 설치 산출물 갱신은 아직 필요하다.
